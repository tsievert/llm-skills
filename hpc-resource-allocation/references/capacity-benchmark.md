# Capacity benchmark (finding the largest input that fits)

Use when the goal is the largest input per job (for example frames per GPU fit), not a safe request for a known job. A capacity ceiling is maximised; headroom margins apply only to the memory later requested.

- **Independent attempts.** One array task per input size, so one failure does not stop the others.
- **Largest first, skip-if-larger-passed.** A descending ladder gives a decisive first result (an all-data attempt that fails at initialisation in minutes) and later rungs are skipped once a larger one passed. Bisect between the last pass and first failure in rounds.
- **Only a program-reported GPU out-of-memory is a ceiling.** Timeout, host RAM kill, NaN or a crash say nothing about GPU capacity: classify them inconclusive and do not bisect on them. Read the program's own status file, not only the exit code.
- **Init failures give a lower bound.** An allocation error reports one failed allocation and the pool size, not the total need, so arithmetic cannot narrow the ladder; use a dense descending ladder because failures are cheap. Inside a bracket, submit a dense set of sizes in one array per round (three rounds instead of about six single-point bisections). Reported peak memory of passing runs is not headroom: a single large buffer can fail while the pool has room, so take the ceiling from the pass/fail bracket plus a margin. For JAX, `device.memory_stats()["peak_bytes_in_use"]` is the measurable peak; `nvidia-smi` shows the preallocated pool.
- **Apply the margin to the memory-driving quantity, not the file count.** When a chunked array passes one chunk and runs out of memory on another, first compare the quantity that drives memory per chunk (valid frames, padded length of the longest recording) and say the hypothesis is untested until then. A chunk with fewer files can still need more memory if padding follows the longest item. A peak close to the pool size means the ladder cannot show headroom.
- **Control run first.** Include one small run at a known-good size in the first round. If it fails like the large ones (for example NaNs at every size), the cause is not capacity and the ladder can stop after one job.
- **Check the ceiling against the production selection rule.** If the real pipeline picks inputs by a rule (for example only complete pre/post pairs), it may not be able to reach the benchmarked size; compare before using the ceiling as a limit.
- **Set the production size a few percent below the largest pass** when its peak use sits at the pool size, and treat a run-time projection from a short benchmark as an upper bound to re-size after one real run.
- **The ceiling is a technical limit; the production size is the user's scientific choice.** If more data per fit is preferable, offer memory-reducing settings (for example serial chunks) as one more test with a stop rule before accepting a cap.
- **Re-measure before cleanup and before large arrays.** Count and size what exists (dry-run listing) instead of trusting earlier notes, and estimate output volume (size per task x tasks) against the quota (ask for the site's quota command; `df` shows the filesystem only).
- **Record context per attempt.** GPU model and partition (see `hpc-gpu-jobs`); the ceiling does not transfer to another partition.
- **Feed the result back** as a generated limits file that the orchestrator reads, and that the job scripts re-read or receive by `--export` (see `hpc-job-scripts`, chaining reference).
- **Ablating settings.** When a bundle of old settings passes and the default fails, run the bundle first, then one single-setting arm per job; this found the one needed setting in one round.
- Ask for the cluster facts (QOS limits, `sinfo` GRES, input sizes) in one batch of questions plus read-only commands before designing the ladder.
